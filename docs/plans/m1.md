Source of truth: docs/build-pack/10-02-m1-client-story-core.md (acceptance criteria). Screens: build pack 5.1 (S1 to S8) and 5.2 (C1 to C4, C15). Format follows docs/plans/m0.md. This plan breaks the build pack down into tasks; where the pack leaves a gap, the default is under Assumptions and must also be logged in docs/decisions.md (chunk 1 does this).

## Goal

Make the client story work end to end on one device: a staff member (Jade) signs in, sees what is due, finds and completes the full Safeguarding and whistleblowing refresher on a phone (lessons, then a quiz drawn by a tested quiz engine, with multiple choice, true or false and branching scenarios, per-question feedback and descriptive Learn more links), passes, and that completion creates Evidence carrying the module version and site; the manager (Priya) sees needs-attention items first on the dashboard, sees Jade turn current without reloading, assigns a module to several people in one action (with notifications), opens people and person records, sees basic module stats, and prints a readable inspector-ready training matrix. It also clears the two M0 known issues (owner roles found by name; `adminCount` ignoring expiry and suspension).

## Assumptions

Chunk 1 copies these into docs/decisions.md under "M1 assumptions".

1. **Jade's starting state.** Section 7.3 has Jade fully current, but Track A step 3 needs her ring to "turn green" and the AC needs C1 to show her becoming current. The seed gives Jade current Safeguarding evidence completed 18 months before today (about 6 months left, outside the amber window, so C1's needs-attention list still matches 7.3) plus an open Assignment of the Safeguarding module made by Priya 3 days ago, due 14 days after today. The staff ring counts open assignments, so Jade starts at "1 to do" and becomes "You're compliant" after passing; C1 moves her from Assigned training to Recently completed with a Current badge.
2. **Needs attention on C1.** Lists only active and on-leave people (never archived). Order: overdue (most days overdue first), then expiring soon (fewest days left first), then not started (by name). Awaiting check items are a separate "Waiting for a check" section directly below (Ben Carter), so the needs-attention list is exactly the six 7.3 items: Mark first aid overdue; Lucy, Hannah and Chris safeguarding and Maureen food hygiene expiring (by date); Amira What changed not started.
3. **Compliance definitions.** A requirement counts as compliant when its status is `current` or `expiringSoon`. C1's ring shows "N of M staff fully compliant" over active and on-leave staff (Little Acorns at seed: 11 of 14). The staff ring's "to do" count is: applicable requirements that are `overdue`, `notStarted` or `expiringSoon`, plus open assignments whose module does not satisfy a requirement already counted; `awaitingCheck` shows as "1 waiting for a check", not as to do. The ring is complete (green, tick, "You're compliant") when to do is 0.
4. **Next up and Coming up.** Next up is the open assignment with the earliest due date; if none, the most urgent requirement (overdue, then expiring soonest, then not started) that a published module satisfies; if none, "You're all caught up". Coming up shows the next three future dates from open assignment due dates and requirement expiry dates within 90 days.
5. **Quiz unlock and retakes.** The quiz starts only when every lesson of the module's current version has a `lessonCompleted` event for this person (from any earlier time). `maxRetakes: null` means unlimited. Starting a quiz with an unfinished attempt for the same module and version resumes it.
6. **Scoring.** An MCQ or true or false question is correct when the chosen option is `correct`. A scenario is correct only when every choice on the path taken is `best`; the reported outcome is the worst outcome on the path (`poor` beats `ok` beats `best`). Score is the percentage of drawn questions correct, rounded down to a whole number. Passed when score >= passMark. "Missed" means not correct.
7. **Draw rules (brief 8).** `mcq` draws only `mcq` and `trueFalse`; `scenario` draws only scenarios; `mix` draws `round(drawCount * mixScenarioShare)` scenarios and the rest from the other types; if one type is short, the other type fills the gap; if the bank is smaller than `drawCount`, every eligible question is used. When `shuffleQuestions` is false the draw keeps bank order (still a random subset when drawCount is smaller); `shuffleOptions` shuffles MCQ options and scenario choices; true or false options are never shuffled.
8. **Learn more visibility (brief 31.1).** After an answer: wrong answer shows every link; right answer shows a link only when the module's `learnMoreFor` is `all` and the link's `showFor` is `all`. Official links (kinds official, legislation, regulator, other) come first, then a "From your organisation" group from the client's overlays. During a closed-book attempt, no links show until results (engine supports it; the closed-book UI is M2). The results screen always shows all links for missed questions.
9. **Display domain.** A link shows its website name: hosts ending `.gov.uk` show `gov.uk`; hosts ending in a two-part UK suffix (`.org.uk`, `.co.uk`, `.ac.uk`, `.nhs.uk`) show the last three labels; anything else shows the last two labels (`nspcc.org.uk`, `legislation.gov.uk` shows `gov.uk`). Organisation documents show the client's display name instead of a domain.
10. **Organisation document.** Section 7.4 calls Little Acorns' Safeguarding policy "a fictional PDF". M1 stores it as an `Attachment` record with a short fictional Markdown body and renders it at `#/doc/:attachmentId` (opened in a new tab, read through the data layer). Real PDF uploads arrive with the overlay editor in M3.
11. **Module visibility.** In M1, every published provider module is visible to every client's actors. Pack-based visibility (nursery versus luxury retail) arrives with M6; logged as a known gap. Client-owned modules and ModulePlacement are M3.
12. **Module-local sub-ids.** Lesson, block, question, option, scenario step and choice ids are module-local keys matching `^[a-z0-9][a-z0-9-]{0,39}$`, unique within the module (not global ULIDs). Learning events store `moduleId` plus the key.
13. **Notifications are stored as kind plus parameters** (`kind: 'trainingAssigned'`, `params: { moduleTitle, dueDate }`), rendered through t(), and carry `clientId` (CLAUDE.md: every client-owned record has clientId). Build pack 6's literal `title` and `body` are replaced.
14. **Assigning.** One batch per C4 action, all or nothing: if any chosen person is outside the actor's write scope, archived or unknown, nothing is written. A person with an open assignment for the same module is skipped and reported, not duplicated. Due date is the end of the chosen London day (23:59) and must be today or later. At most 500 people per action. Each created assignment gets one Notification for the person's staff user (if they have one). No Outbox message in M1 (reminders and channels are M3).
15. **Evidence from modules.** Passing writes one Evidence per requirement in the module's `requirementIds` that applies to the person (`kind: 'module'`, `completedAt = ctx.now`, `moduleId`, `moduleVersion` from the attempt, `language`, `siteIdAtTime = person.primarySiteId`, expiry from the requirement's `renewEveryMonths`). It also marks open assignments for that module `done` and appends `attemptFinished` and `moduleCompleted` events, all in one batch with a slim audit event. Failing writes only the attempt and `attemptFinished`.
16. **Live update.** The store emits a change notice (store names only, no data) after every successful write; the web app invalidates its queries and forwards the notice to other tabs on a `BroadcastChannel('sta-data')` (wrapped in try and catch; same-tab updates still work without it). This is the "live status update from staff to manager" for one device; real push is production work.
17. **S1 data.** The user switch lists the current client's active staff users by display name through a new `DemoAdmin.listStaffUsers(clientId)` (demo shell only; staff actors still cannot read colleagues). Choosing a person and entering PIN 1234 sets DemoState persona to that staff user. A wrong PIN shows "That PIN is not right. In the demo the PIN is 1234."
18. **Content review state.** Modules get an optional `draftContent: boolean`; the Safeguarding module ships with `draftContent: true` and shows a "Draft content" badge on S4 and S6 until the user reviews it (build pack 9.1).
19. **Seed upgrade.** SeedMeta gains `seedVersion` (M1 = 2). On boot, a stored seed with a lower version is reloaded with the same seed value and today (Reset semantics), so a browser that ran M0 picks up the M1 world. IndexedDB schema goes to version 2 (new object stores only).
20. **Learning event visibility.** Client admins with `reports.view` in scope can read learning events and attempts for people in their scope (needed for stats); the UI only ever shows aggregates and per-person status, never raw learnMoreOpened events. Staff read only their own. Provider actors read none in M1 (P5 counts are M4).
21. **Safeguarding quiz settings (placeholders):** mode `mix`, `mixScenarioShare` 0.4, `drawCount` 10, shuffle questions and options on, `passMark` 80, `maxRetakes` null, feedback on, `showSourceRef` true, `notesInQuiz` `choice`, `learnMoreFor` `all`.
22. **Renewal periods stay VERIFY** (user instruction). The Safeguarding refresher uses the existing placeholder `renewEveryMonths: 24`. The content chunk may record what the EYFS text says in decisions.md but does not change requirement values or remove VERIFY markers.

## Design

### Chunk 1 fixes: owner role key and admin count (M0 known issues)

- `roleSchema` gains `systemKey?: 'providerOwner' | 'providerCoOwner' | 'providerAdmin' | 'providerSupport' | 'providerBilling' | 'providerContentEditor' | 'providerReadOnly' | ClientRoleKey`, with a refine: `systemKey` is present if and only if `system` is true. Export a `SystemRoleKey` type and `OWNER_KEYS = { provider: 'providerOwner', client: 'accountOwner' }` from domain.
- `providerRoleTemplates` and `clientRoleTemplates` carry their key; the seed writes it; the contract world sets it on its added system roles.
- `ownerGroup(role)` in `permissions/engine.ts` uses `role.system && role.systemKey === 'providerOwner'` (provider) or `=== 'accountOwner'` (client owner). No name comparison remains anywhere in domain or data (a grep test asserts `'Account Owner'` and `=== 'Owner'` do not appear in `packages/domain/src/permissions/engine.ts` or `packages/data/src/policy.ts`).
- Export `isAssignmentActive(assignment, now)` from domain (status `active` and `expiresAt` absent or strictly after now) and use it inside `effectivePermissions` and in the data layer.
- `policy.ts` approval: `isAccountOwner` uses `systemKey === 'accountOwner'` on an assignment that is active at `ctx.now`. `adminCount` counts distinct client-side users of the submission's client whose UserAccount `status` is `active` and who have at least one assignment for which `isAssignmentActive` is true at `ctx.now`.
- Client actors still cannot write system roles; a client-written role with `systemKey` is `ValidationError` (schema) or `ForbiddenError('permission')`.

### Domain package (packages/domain)

New schemas in `schemas/learning.ts` (Zod, field names as build pack 6 except where Assumptions say):

- `learnMoreLinkSchema`: `id` (local key), `title`, `url?` (must parse with `new URL`, protocol `https:`, no username or password), `attachmentId?` (exactly one of url and attachmentId), `publisher`, `kind`, `locator?`, `language`, `showFor`, `lastCheck?`.
- `contentBlockSchema`: the five block kinds of build pack 6.
- `lessonSchema`, `questionSchema` (refines: `mcq` has 2 to 6 options with exactly one correct; `trueFalse` has exactly 2 options with one correct; `scenario` has `scenario.steps` with 1 to 4 steps, the first step is the entry, every `next` points to a later step in the same question, at least one path ends in `best`, no cycles; `explanation` non-empty; `learnMore` has at least one link when `sourceRef` is set), `quizSettingsSchema` (`drawCount` >= 1, `mixScenarioShare` in 0..1 and required when mode is `mix`, `passMark` 0..100), `moduleSchema` (adds `draftContent?`; unique local keys across lessons, questions, options, steps and choices; `version` >= 1).
- `clientLinkOverlaySchema` (adds `id`), `attachmentSchema` (`id`, `clientId`, `title`, `mime: 'text/markdown'`, `body`, `createdAt`), `assignmentSchema`, `learningEventSchema` (adds `linkId?` for `learnMoreOpened`, `optionId?`, `choiceIds?`), `attemptSchema` (adds `clientId`, `siteId`, `optionOrder?: Record<questionKey, string[]>`), `notificationSchema` (Assumption 13).

New pure modules, each with a comment citing the brief section:

- `quiz/draw.ts`: `drawQuestions(module, rng) => { questionIds: string[]; optionOrder: Record<string, string[]> }` (Assumption 7).
- `quiz/score.ts`: `checkAnswer(question, answer) => { correct: boolean; outcome?: 'best' | 'ok' | 'poor' }` where `answer` is `{ optionId }` or `{ choiceIds: string[] }`; `walkScenario(question, choiceIds)` validates the path (each choice belongs to the current step and `next` leads to the following step; the path ends at a choice with no `next`), else throws `InvalidAnswerError`; `scoreAttempt(questionIds, answers, module, passMark) => { score, passed, missedQuestionIds }`.
- `quiz/learnMore.ts`: `visibleLearnMore({ question, overlays, correct, settings, phase: 'feedback' | 'results', attemptMode })` returns `{ official: LearnMoreLink[]; organisation: LearnMoreLink[] }` (Assumption 8); `displayDomain(url)` (Assumption 9); `isSafeHttpsUrl(url)`.
- `progress/staff.ts`: `staffSummary({ person, site, requirements, evidence, submissions, assignments, modules, now, amberWindowDays })` returns per-requirement rows (status, last done, next renewal, cadence months, satisfying published module id), `toDo`, `waiting`, `complete`, `nextUp`, `comingUp` (Assumptions 3 and 4).
- `progress/client.ts`: `needsAttention(...)` and `waitingForCheck(...)` (Assumption 2), `complianceByRequirement(...)`, `orgCompliance(...)` (Assumption 3), `recentlyCompleted(evidence, people, now, days = 14)`.
- `progress/matrix.ts`: `trainingMatrix({ people, requirements, evidence, submissions, teams, now, amberWindowDays, siteId? })` returns `{ columns: Requirement[]; groups: { team: Team | null; rows: { person; cells: { status; date?; daysLeft? }[] }[] }[] }`: active and on-leave people only, grouped by first team in team order then by last name; a column for each requirement that applies to at least one listed person; a cell is `notAssigned` when the requirement does not apply. `matrixCsv(matrix, t)` returns RFC 4180 text with formula-injection guarding (cells starting with `=`, `+`, `-` or `@` are prefixed with `'`).
- `progress/moduleStats.ts`: `moduleStats({ module, assignments, attempts, events, evidence, now })` returns the headline numbers and the per-question rows (answered, percent correct, Learn more opened; hardest first, ties by bank order).
- `assign.ts`: `planAssignment({ moduleId, people, existing, dueAt, now })` returns `{ toCreate: personId[]; skipped: { personId; reason: 'alreadyAssigned' }[]; invalid: { personId; reason: 'archived' | 'unknown' }[] }`, plus `dueAtFromLondonDate('2026-11-02')` (23:59 London).

### Data package (packages/data)

- New stores and repositories (IndexedDB schema version 2, `clientId` index where present): `modules` (read), `clientLinkOverlays` (read), `attachments` (read), `assignments` (read), `learningEvents` (read), `attempts` (read), `notifications` (read). None of these has a generic `put` for actors in M1; writes go through the operations below. Seed and tests write through `DemoAdmin.bulkPut`.
- Read rules (policy table): modules: provider-owned published modules readable by any known actor (provider needs `content.read`), drafts by provider only; overlays and attachments: any client or staff actor of the same client; assignments: client actor with `assign.view` in read scope of the person's sites, staff own person; learning events and attempts: client actor with `reports.view` in scope, staff own; notifications: own `userId` only, every side. Cross-client records are NotFound on get and omitted from list, as in M0.
- New error `RuleError(code)` extends `DataError` (`code: 'rule'`), with `rule: 'lessonsIncomplete' | 'noRetakesLeft' | 'attemptFinished' | 'alreadyAnswered' | 'notInAttempt' | 'notAllAnswered' | 'moduleNotPublished' | 'invalidAnswer' | 'dueInPast' | 'tooMany' | 'invalidPeople'`. The web app maps each to `errors.rule.<rule>`.
- `learning` service (staff actor only; any other side gets `ForbiddenError('permission')`; account state must allow `staffOwnRecord`; every write appends events with `clientId`, `siteId` = person's primary site, `personId`, `at = ctx.now`):
  - `recordLesson(ctx, { moduleId, lessonId, kind: 'viewed' | 'completed' })`: lesson must exist in the current version.
  - `startAttempt(ctx, moduleId) => Attempt`: published module only; Assumption 5; draws with `drawQuestions(module, rng.fork(attemptId))` from the store's RNG; writes the Attempt and `attemptStarted`.
  - `answer(ctx, { attemptId, questionId, optionId? , choiceIds? }) => { correct, outcome? }`: own unfinished attempt (another person's attempt is NotFound); question in the attempt; not already answered; correctness computed here from the stored module (never from the caller); writes `questionAnswered` with `correct`, `scenarioOutcome`, `optionId` or `choiceIds`.
  - `finishAttempt(ctx, attemptId) => { attempt; passed; score; missedQuestionIds; evidence: Evidence[] }`: every drawn question answered; scores with `scoreAttempt`; one batch per Assumption 15; audit action `evidence.moduleCompleted` storing only `{ attemptId, evidenceIds, moduleId, moduleVersion }`.
  - `learnMoreOpened(ctx, { moduleId, questionId?, lessonId?, linkId, attemptId? })`: the link must exist on that question or lesson, or in one of the client's overlays for it; writes exactly one `learnMoreOpened` event and nothing else (no XP, no other store).
- `assignments.assign(ctx, { moduleId, personIds, dueAt }) => { created: Assignment[]; skipped: {...}[] }`: client actor with `assign.manage` in write scope covering every chosen person; Assumption 14; `featureAvailability(state, 'coreCompliance') === 'yes'`; writes assignments, notifications and one audit event `assignments.created` with `{ moduleId, count }` (no names) in one batch.
- `notifications.markRead(ctx, ids)`: own notifications only; sets `readAt = ctx.now`.
- People archive uses the existing `people.put` (status `archived`, `leftDate = ctx.now`, `staff.manage`); it also sets the person's open assignments to `cancelled` in the same batch.
- `StoreHandle.subscribe(listener: (stores: StoreName[]) => void): () => void`, called after each successful `apply` (both adapters, implemented once in `createStore`).
- `DemoAdmin.listStaffUsers(clientId)` returns `{ userId, displayName, personId }[]` for active staff users of that client, sorted by display name.

## Security and privacy

- **Inputs and validation.** Every new record is Zod-validated, including content in CI. Answers carry only ids; the data layer checks they belong to the attempt and module and computes correctness itself, so the UI cannot award a pass or Evidence. C4 input: module id must be a visible published module, people ids must be in scope, due date parsed as a London calendar date and not in the past, at most 500 people. Search text is used only for in-memory filtering. Route params are looked up through the data layer (NotFound for anything outside tenancy).
- **Authorisation (OWASP A01).** New stores follow the M0 policy: cross-client records are NotFound; staff read only their own learning data and notifications; assign needs `assign.manage` in write scope for every person; stats and matrix need `reports.view`, CSV needs `reports.export`; Evidence can only be created by an approved submission (M0) or a passed attempt (M1). Attempts are bound to their person (IDOR checks). The UI gates with `can()`, never role names; K-1 removes the last role-name check from the policy.
- **XSS and links (OWASP A03).** Lesson Markdown is rendered to React elements by an allowlisted renderer (no `dangerouslySetInnerHTML`; lint already bans it); raw HTML, links and images in lessons are refused by content tests. Learn more URLs must be https without credentials (schema and render-time check); links use `target="_blank"` with `rel="noopener noreferrer"`, never frames (brief 31.4). Organisation documents render as text through the same renderer. CSV export guards against formula injection.
- **Secrets and config.** None added. The demo PIN 1234 is a published demo value (build pack 2.2) and S1 carries the Demo only badge.
- **Data exposure and privacy.** Fictional names only (allowlist test extended to content). Learn more opens are stored per person but shown to admins only as counts; provider actors read no learning data. Notifications are own-only. Audit events for assignments and module evidence store counts and ids, not names or answers. The BroadcastChannel carries store names only. The printed matrix and CSV carry personal data and say so in the header; generating them needs `reports.view` or `reports.export`. Learner notes do not exist yet (M2).
- **No network.** Learn more links are ordinary links opened by the user in a new tab (CLAUDE.md); the app itself still makes no requests (CSP `connect-src 'self'`, no-network e2e). Tests stub any popup navigation.
- **OWASP A04 Insecure design.** Quiz rules (unlock, retakes, scoring, one answer per question, finish once) live in pure domain functions and are enforced by the data layer. Speed is never rewarded (no timer, no time-based scoring).
- **OWASP A08 Integrity.** No new dependencies. Content is validated in CI; a content edit that breaks a link rule fails the build.

## Dependencies

None added. A Markdown subset renderer, CSV writer, display-domain helper and print stylesheet are each a few dozen lines. Playwright's built-in `page.pdf` and `page.clock` cover the print and clock needs. `BroadcastChannel` is a browser built-in. If the implementer finds a real need (for example a PDF text extractor for tests), it must be justified in decisions.md, pinned exactly and checked for typosquats; prefer not to.
