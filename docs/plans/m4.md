## Assumptions and conflicts

Defaults where the pack is silent (record each in docs/decisions.md when built):
1. D3 was not read for this plan. Confirm its scope in 5.4 before the Track B chunk.
2. Routes follow the pack. P2, P7, P11, P14 and P18 replace existing placeholders; the rest are new routes.
3. Step-up code for price confirmation reuses the simulated 2FA code in `packages/domain/src/twoFactor.ts`.
4. Ownership transfer cooling-off default is 7 days (placeholder), skipped by Fast-forward through the Clock.
5. Recovery cooling-off default is 24 hours (placeholder); two approvers must be different provider users.
6. Price change notice defaults to 30 days; a change with no end date runs until cancelled.
7. Update billing name to match applies to invoices issued after the update; issued invoices are never edited.
8. Link check is simulated and deterministic: only the seeded broken link fails. No network requests.
9. Provider module feedback shows names removed (brief 19.1); learner notes are never exposed.
10. Provider permissions use can() and entitled(); no role-name checks in the UI.
11. Both adapters must pass every new contract test; new stores need tenancy and audit via `policy.ts` and the newStoresPolicy test.
12. No conflict between brief and pack found so far. If one appears, follow the brief and log it.

## Security notes

- Step-up code: confirming a price change needs the Confirm price changes permission and a valid simulated step-up code (reuse `twoFactor.ts`). A wrong or missing code leaves the adjustment awaiting confirmation and writes a failed-attempt audit entry. Preview and draft never change a price.
- Provider RBAC: every provider op and page checks can() (and entitled() where a feature applies), never role names. Provider data ops enforce this in `policy.ts`, so a client actor is denied every provider op. New stores are deny-all until wired and covered by the newStoresPolicy test.
- Internal notes: ticket internal notes are stored with an internal flag and never returned to a customer or staff actor. A contract test proves the customer projection omits them. Learner notes are never exposed to the provider.
- Recovery: a recovery request needs two different approvers (distinct provider users, and not the requester). The same approver twice is rejected. Cooling-off runs on the Clock. Recovery never bypasses export of compliance records.
- Ownership transfer: needs acceptance by the new owner, simulated 2FA confirmation and the cooling-off period. The last owner cannot be removed.
- No payment wording to staff: banners, notices and the price notice on the plan card and calendar are shown only to billing permission holders. Staff see only the neutral account notice from M3.
- Audit: every provider action that changes state (price confirm, cancel, billing-name action, transfer, recovery, role change, maintenance toggle, announcement, client creation, module publish, ticket assignment) writes an audit entry with actor, clientId where relevant, and time from the Clock.
- Content: only fictional data, no real names or branding in seed, announcements, saved replies or prize text. The link check makes no network request. Learn more links stay ordinary links.
- Tenancy: all client-owned new records carry clientId (and siteId where relevant). Cross-client reads (open counts, P1 totals) go through provider-only ops.
