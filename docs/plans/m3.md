## Goal

Give client admins the depth a real nursery manager or group needs, on top of the M1 compliance core and the M2 engagement layer, while staff gain the matching self-service pieces. Admins build and version their own modules from pasted Markdown (with phone preview and a publish checklist), add their own learning links and PDFs to any module through an overlay, see full module stats and module feedback, set auto-assign rules and reminder policy (messages only ever reach the Outbox), plan with a team calendar and first aiders forecast, approve uploaded certificates, manage roles, two-factor sign-in (simulated), the organisation name, billing and add-ons (fake data), themes with contrast guardrails and schedules, data exports and person erase, and see calm account-state banners that follow the brief 24.4 matrix. Multi-site clients get a site switcher, grouped people, site comparison, leaderboard scopes and a fair Sites board. Staff get notifications with snooze and quiet hours, Help with FAQs, feedback and tickets with screenshots and a blur tool, certificate upload, a calendar with .ics export, and the module feedback card, lesson thumbs and Report a problem. Track A steps 2, 6, 8, 9 and the certificate part of step 5 run as automated tests.

## Assumptions

Chunk 1 copies these into docs/decisions.md under "M3 assumptions".

### Personas, sign-in and two-factor

1. **Client persona switching.** `DemoState` gains `clientPersona: { userId }` (default Priya). D2 "Jump to persona" lists the client admins of Little Acorns, Oak Tree and Willow Lane (Priya, Daniel, Fiona, Tariq, Colin, Rosa, Gemma) and a few staff (Jade, Mark, Maureen, Oscar at Riverside, Toby at Meadow). The actor's `clientId` comes from the chosen user's record, not from a hard-coded Little Acorns key (App.tsx today hard-codes it). Staff persona switching stays on S1.
2. **C26 is simulated.** Choosing a persona counts as signed in; C26 shows the email and password step (any password accepted, Demo only badge), then the code step for enrolled admins (demo code 123456) or enrolment for those who are not. Sign-in is not forced on every visit.
3. **Two-factor grace.** `UserAccount` gains `twoFactorRequiredSince` (set for every client admin). Grace is 7 days (placeholder). Within grace the admin sees a calm "Set up two-step sign-in, N days left" banner. After grace and until enrolled the admin is limited: every client-side data-layer call except own `users.get`, `access.permissions`, `me.*`, `twoFactor.*`, `faqs.*` and own `tickets.*` throws `ForbiddenError('twoFactorRequired')`, and the shell sends them to C26 enrolment. Staff users are never asked (no field, gate never applies to `side: 'staff'`).
4. **Enrolment** shows a QR code (generated on the device from an `otpauth://` URI with a seeded demo secret) and the manual key, then asks for a code; 123456 confirms. Ten recovery codes are shown once (download as .txt, print) and stored only as SHA-256 hashes (`twoFactor.recoveryCodeHashes`), so a used code is checked and removed. Five wrong codes lock code entry for 15 minutes (`twoFactor.lockedUntil`). Step-up (a fresh code) is required for plan changes, billing contact changes, export all data and person erase.
5. **Seeded 2FA states:** Priya, Fiona, Tariq, Rosa and Gemma enrolled; Daniel required since 2 days ago (within grace); Colin Reeve (Hillside site manager) required since 12 days ago (limited). Provider members keep their M0 states.

### Roles, team and organisation

6. **Billing permissions** follow brief 23.1: `billing.view` covers view billing and download invoices; new `billing.manageAddOns` (Allow under Settings and billing at Manage); `billing.manage` stays "Manage plan and payment". Account Owner gets all three, Group Admin `billing.view` and `billing.manageAddOns`, every other template none. Roles are recompiled in the seed.
7. **Team page** reads with `staff.view`; inviting, changing roles or scope and custom roles need `team.manageRoles`, guarded by `canGrant` (only permissions the granter holds) and `lastOwnerGuard`. Invites create an invited `UserAccount`, an `Invitation`, an Outbox email and an audit event. Custom roles start from a template, flip category levels and Allow toggles, count against `customClientRoles`. Preview as this role is a read-only panel listing the screens and actions the role allows (computed with `can()`), not a live impersonation. Promote in two taps and ownership transfer are out of scope.
8. **Activity log** is the client's audit events, readable by client actors with `team.manageRoles`; entries carry ids, action names and counts, never note text, feedback text or file contents.
9. **Organisation profile.** Display name 2 to 60 characters, short name up to 20, trimmed, no control characters, not only digits or punctuation (placeholders). `organisation.updateProfile` needs `org.editName`, appends `nameHistory` with `reviewStatus: 'pendingReview'`, writes an audit event with old and new names. Staff see the new name at once through the change notice on `clients`. Certificates use `displayNameAt(client, evidence.completedAt)`; exports (CSV, matrix, ZIP, person export, invoices excepted) add "formerly {old}" for 90 days after a change (`formerlyNote`, placeholder 90). Invoices always use `billingNameAtIssue`.
10. **Onboarding checklist** steps (brief 26.1): invite staff (any invited or added person), check reminder settings (policy saved once), assign first training (any manual assignment), set up a competition (any published competition), export a first training matrix (matrix print or CSV opened once, recorded by `onboarding.markDone(ctx, 'exportMatrix')`). Little Acorns is seeded with all but "set up a competition" done (build pack 7.2).

### Authoring, links and module feedback

11. **Versions.** A published module is the `modules` record. Editing a published own module writes a `ModuleDraft` (one per module, key `moduleId`). Publishing checks `publishChecklist`, snapshots the previous published version into `moduleVersions` (key `moduleId:version`), writes the draft as version n+1, and deletes the draft. A never-published module lives in `modules` with `status: 'draft'`, version 1. Evidence, attempts and events keep the version they were taken on; results, certificates and C8 read old question text from `moduleVersions`. The publish dialog asks "Ask people who completed version n to take it again?"; yes creates assignments (due in 30 days, placeholder) for people with Evidence or a pass on an older version.
12. **Markdown import.** `markdownToLessons`: `#` or `##` headings start lessons (text before the first heading becomes lesson 1 "Introduction"); paragraphs become `text` blocks; a list under a heading named "Key points" (any case) becomes `keyPoints`; lines starting `> ` become an `info` callout; images, HTML and links to non-https URLs are dropped with a warning list. Lesson minutes are estimated at 200 words per minute, at least 1. Lesson ids are slugged local keys, made unique.
13. **Builder questions**: multiple choice (2 to 6 options, at least one correct) and true or false, each with explanation (required), optional source reference and links. Branching scenarios are authored only by the provider in the PoC; JSON export is supported, JSON import is out of scope.
14. **Publish checklist** (brief 5.1): title 3 to 100 characters; at least one lesson with text; at least one question; quiz settings valid (`drawCount` 1 to bank size, pass mark 1 to 100, mode possible with the bank); a linked requirement or the explicit "This module is optional" choice; every link https. Failing items are listed; publish is refused in the data layer with `RuleError('checklistFailed')`.
15. **Provider modules are read-only for clients**: any module write by a client actor on `owner: 'provider'` gives `RuleError('providerModuleReadOnly')`. Duplicate creates an own draft copy (`duplicatedFrom: { moduleId, version }`, version 1, new local keys kept) with the note "This copy is yours. It will not get our updates and you are responsible for keeping it accurate." Duplicates count against `ownModules`. Archive is always allowed; delete only when nobody has Evidence, a pass or a `moduleCompleted` for it (`RuleError('hasCompletions')`).
16. **Site modules.** An own module may carry `owner.siteId`; it is visible only to that site's people, editable by actors with `modules.manage` in that site's write scope; group modules need whole-organisation scope.
17. **Overlay links** (`modules.addLinks`): `clientLinkOverlays` keyed by client, module and question or lesson local key; each link https (`isSafeLink`) or an `attachmentId` of a client learning document (PDF); title 1 to 120 characters, up to 10 links per target; kind `organisation`, publisher the client display name. Overlays never change the module. When a new provider version drops a question or lesson, its overlay stays stored but is not shown to staff, and C7 lists it under "No longer in this module" with Remove. Every overlay change writes an audit event. Own modules keep links inside the module content (builder fields) and use the same validation.
18. **Module feedback.** Kinds `moduleCard` (rating 1 to 5, tags, comment up to 500), `lessonThumb` (up or down, optional tag), `questionReport` (tag Mistake in a question, optional text). Quick tags from brief 19.1 (content list). Anonymous items store no `personId` and no user id at all (only client, site, module, version and target), so a name cannot appear anywhere; reply to them gives `RuleError('anonymousNoReply')`. Replies notify the person's staff user (in-app). Provider projection (`feedback.read`): items on provider modules with `personId`, `siteId` and reply text removed, grouped per module, question reports first; for client-own modules only `{ clientId, moduleCount, itemCount }`. App feedback is readable only by the provider (`feedback.read`), never by any client actor. Feedback text is plain text with a reminder not to name children or colleagues.

### Evidence, files and tickets

19. **File attachments.** `Attachment` becomes a union: the M1 markdown document (`kind: 'document'`, default for old records) and `kind: 'file'` with `purpose: 'certificate' | 'ticketScreenshot' | 'learningDocument'`, `mime` in `image/jpeg`, `image/png`, `image/webp`, `application/pdf`, `bytes`, `data: Uint8Array`, `ownerUserId`, `personId?`, `siteId?`, `redacted`, `alt?`. The data layer checks magic bytes against the mime, 10 MB per file, 50 MB per device in total (`RuleError('storageFull')`, placeholders), and refuses JPEG with an APP1 Exif or XMP segment, PNG with `eXIf`, `tEXt`, `iTXt` or `zTXt` chunks and WebP with EXIF or XMP chunks (`RuleError('imageMetadata')`). The app always re-encodes images through a canvas (max edge 1600 px, JPEG quality 0.8, orientation applied), which removes metadata and compresses; the data-layer check is defence in depth.
20. **File read rules** (closing the M1 decision about per-person files): certificate files are readable by the person, client actors with `evidence.view` whose read scope includes the submission's site, and nobody on the provider side; ticket screenshots by the raiser, and by client actors with `support.viewOrgTickets` when the ticket is an admin ticket or a staff ticket shared with the manager; learning documents by everyone in the client. Everything else is NotFound.
21. **PDF viewing.** PDFs open in a new tab from a `blob:` URL created with the stored mime (`application/pdf` only) via an Open the PDF button; images show inline with zoom (`img-src blob:` is already allowed). No PDF library and no CSP change.
22. **Submissions.** Staff submit for their own requirements that accept external evidence and apply to them; admins with `evidence.uploadForOthers` in scope upload on someone's behalf (a different person must approve unless the single-admin rule applies). One open submission per person and requirement: Resubmit updates the same record (new file and details, back to `awaitingCheck`, history in the audit log). Expiry: `fromCertificate` requires the entered expiry; `fromRenewalPeriod` computes `completedAt + renewEveryMonths` and shows it as "Expected expiry". Decisions: Approve (optionally correcting completed and expiry dates, both recorded in the audit with before and after), Ask for a better copy (note required, 1 to 300), Reject (reason from: Not the right course, Name does not match, Certificate has expired, Cannot read it, Other; plus optional note). Approval needs `coreCompliance` availability `yes` (stops in Read-only); upload follows `staffOwnRecord`. Each decision notifies the person. "Waiting" uses London working days (Monday to Friday, no bank holidays in the PoC); more than 3 working days is highlighted (placeholder).
23. **First aiders.** The nursery pack names its first aid requirement (`firstAidRequirementKey: 'paediatricFirstAid'`). The print list shows active people with current Evidence for it (any kind; approved external certificates show who approved and when). The forecast counts, per site and for each of the next 12 London weeks, active people (not on leave) whose Evidence for it is current on that week's Monday, warning when below `ClientSettings.firstAiderThreshold` (default 2, placeholder).
24. **Tickets (customer side).** Feature list (about 15, grouped by area) and issue types from brief 25.3 live in packages/content; Other needs 3 to 80 characters. Impact sets priority (I can't use the app: high; workaround: normal; question: low). Title 3 to 100, description 1 to 2,000, reply 1 to 2,000. Up to 5 screenshots per message. Context attached: screen route, feature area, module and lesson ids when present, side, client and site ids, app version, browser name from the user agent, account state; each item has a Remove button and only what remains is stored. Staff tickets are private to the raiser and the provider unless Share with my manager is on; `ClientSettings.allowStaffTickets` off hides the action and the data layer refuses. Ticket numbers are `T-` plus a 4-digit sequence starting 1001. Provider replies and status changes are M4 (the seed includes one provider reply so S16 and C23 show a thread).

### Rules, reminders and notifications

25. **Auto-assign triggers in M3**: `personAdded` (fires in the same batch as `people.add`), `roleChanged` (fires in the batch of a job role change through `people.update`), `requirementExpiring` (fires in the scheduled job when a person's Evidence for `requirementId` expires within `days`). Other brief triggers (moved site, start plus N days, new module version) are later. Filters: job roles, teams, sites (a person matches a list if any of theirs is in it). Action: a module or a group (expanded into one module assignment per group module). Safeguards: never a duplicate open assignment for the same person and module; nothing assigned when the module satisfies a requirement that is already current and not expiring within the rule's window; people on leave, invited or archived are skipped; manual assignment always allowed. Each created assignment has `source: { ruleId }`. Rules count against `autoAssignRules` when enabled. Creating or enabling needs `authoring` availability.
26. **Plain-language sentence** comes from language keys with parameters, for example "When someone joins as Practitioner at any site, assign New starter induction, due in 14 days" and "60 days before Safeguarding expires, assign Safeguarding and whistleblowing, due on the expiry date". Affected-now preview: `personAdded` and `roleChanged` count matching active people who do not have the module open or current (who would get it if they joined now); `requirementExpiring` counts people inside the window right now without an open assignment.
27. **Scheduled jobs.** `DemoAdmin.runJobs(now)` is the server-cron stand-in: it runs `requirementExpiring` rules, reminders and add-on period ends for every client, idempotently. The app calls it after boot and after every Fast-forward, Back to today and Reset. Contract tests call it directly.
28. **Reminders** (policy per client; `ClientSettings.reminderPolicy` already exists): staff reminders for assignments due in 7 and 1 days (policy `dueOffsetsDays`) and overdue (once, on the first overdue day, then weekly), and for expiry at 60, 30 and 7 days (`expiringOffsetsDays`). Each reminder is one in-app Notification plus one Outbox message (`push` for staff users, `email` for admins), and a `reminderLog` entry keyed `personId:kind:targetId:offset` so it is never sent twice. Guardrails: weekly cap per person per London week (counts every reminder and manager chase; default 3), quiet hours (client policy and the person's own `prefs.quietHours`; reminders falling inside wait for the next run outside them), people on leave or with `pausedUntil` in the future get none, requirements awaiting check get none, and a reminder is re-checked at send time so nothing goes once the training is done. Limited accounts: in-app only (no Outbox). Read-only and Closed: none. Nothing is ever sent anywhere but the Notification and Outbox stores.
29. **Templates and tone.** Three tone presets (Friendly, Neutral, Brief) per reminder kind in the language file; admins may edit the text (1 to 300 characters) using only `{firstName}`, `{training}`, `{date}` placeholders; unknown placeholders are refused. Rendered as plain text. Digest preview lists overdue and expiring people for the admin's scope (never sent to staff). Chase all overdue shows a preview (who gets one, who is skipped and why: cap, paused, quiet hours, awaiting check) and then sends. Send reminder on C3 is the same for one person. Both need `reminders.manage`.
30. **Notifications (S13).** Snooze sets `snoozedUntil` to 08:00 London tomorrow (hidden until then). Quiet hours on S13 write `prefs.quietHours` through `me.updatePrefs`. Game and competition notifications stay off (none are generated in M3).

### Calendars

31. **Calendar items are derived, never stored** (`calendarItems`). Staff items: assignment due dates, renewal and expiry dates per requirement with "start your refresher" on expiry minus the amber window, certificates awaiting check, competition start, end and winners-announced dates (end date) for competitions the person can see, the weekly goal marker on the current week only, and the person's own leave pause start and end. Admin items in scope: expiries grouped by requirement and London week (clusters), assignment deadlines, expected rule refresher dates (expiry minus rule days for enabled `requirementExpiring` rules), awaiting check with waiting time, competitions (start, end, record winners), scheduled themes, leave and return dates, new starters' start dates, and, only when the data layer returns billing data (`billing.view`), plan renewal, invoice due dates, add-on trial ends and the next account state change. Battles, announcements and maintenance arrive with M4 and M7.
32. **Range** is today to 90 days (See further adds 90 days at a time up to 365). Times are London dates; items are all-day.
33. **.ics files** (RFC 5545): `VCALENDAR` with `PRODID`, `VERSION:2.0`, one `VEVENT` per item with `UID` (hash of the item id and the domain `sta.invalid`), `DTSTAMP` from the injected clock, `DTSTART;VALUE=DATE`, `DTEND;VALUE=DATE` (next day), `SUMMARY` (item title only); CRLF line endings, line folding at 75 octets, text escaping. No description, location, names of other people, links or ids. Admin exports use titles without names ("3 Safeguarding expiries"), so a team .ics file holds no personal data either.
34. **Assign refresher for a week** opens a confirm sheet listing the people in the cluster, the module that satisfies the requirement and a due date equal to the earliest expiry in that week; it calls `assignments.assign` once (people with an open assignment are skipped and shown).

### Multi-site and leaderboards

35. **Multi-site UI appears only when the client has more than one active site.** The site switcher (All sites or one site the actor can read) is session state in the client shell and filters every client list and stat (C1, C2, C8, C9, C15, C27, C28, C29, C3 lists) through the domain views; the data layer still enforces scope. Site Managers only see their own sites in the switcher.
36. **Floating staff** are counted once, at their primary site, in every roll-up; under a filtered additional site they appear in an "Also works here" list that is not counted.
37. **Site comparison (C1)**: per site compliance percentage, overdue, expiring, completion rate (assignments due in the last 90 days completed on time) and staff count, sorted with the site needing most attention first (lowest compliance, then most overdue). Tapping a site sets the switcher.
38. **Scopes.** `availableScopes(sites, viewerSite)`: My site always (for a person with a site); My region when the client has sites in more than one region; My country when sites span more than one country; All sites when the client has more than one site. Staff see a scope only when it applies and C14 has switched it on for that board (default My site only). At wider scopes names show as first name, initial and site ("Jade M., Little Acorns"). Admins choose All sites, a region or a site.
39. **Sites board measures** (London month or quarter): Compliance (percentage of applicable requirement items current or expiring soon among eligible people), On-time completion (percentage of assignments due in the window completed by their due date), Participation (percentage of eligible people with any learning event in the window), Knowledge (modules mastered in the window per eligible person, shown to one decimal place). Eligible people: active, not on leave, started at least 14 days ago (placeholder), primary site only. ### Themes

51. **Theme tokens** are an allowlist: `primary`, `accent`, `backgroundTint`, `radius` (`sm`, `md`, `lg`), `fontPairing` (from a list of three system font stacks; no web fonts). ## Security and privacy

- **Inputs and validation.** Every record is Zod-validated in the data layer. Free text (feedback, tickets, replies, notes on decisions, rule names, theme names, organisation names, reminder templates) is plain text with length limits, rendered as React text nodes, never Markdown or HTML; reminder templates allow only three placeholders. Markdown pasted into the builder goes through `markdownToLessons`, which drops HTML and images and keeps only https links; module text renders through the existing safe Markdown component. URLs: https only (`isSafeLink`), shown with their domain, opened in a new tab with `rel="noopener noreferrer"`. Files: magic-byte sniffing, mime allowlist, size and storage caps, metadata refusal, re-encoding of images on the device; blob URLs are created only with the stored allowlisted mime, so an uploaded file can never be served as HTML in the app's origin (stored XSS). CSV cells use the formula guard (OWASP A03 injection). Search and filter input is never turned into a regular expression.
- **Authorisation (OWASP A01).** Every operation checks permission, scope and tenancy in the data layer; the UI uses `can()` and `entitled()` only. New sensitive paths: billing (`billing.view`, `billing.manageAddOns`, `billing.manage`, with Daniel's refusal as a test), evidence approval (`canApproveEvidence`: no own upload, nothing about yourself, site scope), files (assumption 20; provider never sees certificates), module feedback (anonymous items carry no identity at all; provider projection strips ids), app feedback (provider only), tickets (private to raiser unless shared), team changes (`canGrant`, `lastOwnerGuard`), erase (`staff.delete` plus step-up), exports (scope-filtered, never notes or prefs). Mass assignment: settings and profile updates accept allowlisted fields only; `evidenceSubmissions.put` is no longer callable by actors.
- **Authentication (OWASP A07).** Two-factor is simulated (fixed demo code, Demo only badge) and must say so; the gate is enforced in the data layer, recovery codes are stored hashed and single-use, code entry locks after 5 failures. The review checklist states plainly that no real security exists in the PoC.
- **Insecure design (OWASP A04).** Reminders cannot spam (cap, quiet hours, pause, de-duplication log); rules cannot duplicate assignments; the Sites board uses percentages only and never shows a bottom list; small sites are marked; nothing mixes clients; no measure reads speed.
- **Privacy and data exposure.** Calendar files hold titles and dates only; team calendar exports hold counts, not names; ZIP and person exports exclude notes and prefs; anonymised erase keeps only compliance evidence; feedback and tickets remind people not to include children's or colleagues' names; image metadata (including location) is removed; Demo AI logs nothing personal and is grounded only in the lesson; audit events carry ids and counts (the organisation name change is the only one with names, by brief 30.2). Staff never see payment wording.
- **Secrets and config.** None. Demo codes (PIN 1234, 2FA 123456) are public demo values. TOTP secrets are random demo values from the seeded RNG and are not used for real verification.
- **No network.** Everything runs on the device; uploads, ZIP, .ics, QR and Demo AI make no requests (no-network e2e). CSP unchanged (`img-src 'self' data: blob:` already allows image previews; PDFs open as top-level blob navigations).
- **Vulnerable components (OWASP A06).** Two new dependencies (below), pinned exactly, licences checked, lockfile committed, `pnpm audit` in check.sh.

## Dependencies

- `fflate` (exact version pinned at install; a web search on 26 October 2026 reported 0.8.3, MIT, no dependencies, about 50 million weekly downloads; 0.8.3 fixes a denial-of-service bug in `unzipSync`, so pin 0.8.3 or later). Needed to build the ZIP export on the device; writing ZIP with CRC-32, DOS dates and UTF-8 names by hand is error-prone. Also used in e2e to read the ZIP back. Added to apps/web. Check the name on the registry (similar names such as `fflate-unzip` are different packages).
- `qrcode-generator` (exact version pinned at install; the same search reported 2.0.4, MIT, no dependencies, ships ESM and its own types, by kazuhikoarase). Needed for the 2FA enrolment QR code "generated on the device" (brief 22.6); QR encoding with Reed-Solomon is not a few lines. Added to packages/ui. If the registry shows it unmaintained or with advisories, use `qrcode` instead and record why.
- Record versions, licences and the checks in decisions.md. Nothing else: charts, calendar, .ics, image processing (canvas), contrast maths, Markdown import, CSV and hashing (Web Crypto) use the existing stack and browser built-ins.

## Risks and open questions

- **Size.** This is the largest milestone (21 chunks, several large). Keep chunks thin by reusing M1 and M2 views and components; split large chunks at clean points; if time runs short use the cut list above with decisions entries rather than skipping tests.
- **Persona plumbing (chunk 1)** touches every client screen's actor; regressions in M1 and M2 tests are likely and must be fixed by correcting the actor, not by changing assertions.
- **Derived account state.** If M0 to M2 code reads `client.accountState`, switching to the derived state may move seeded summary clients; seed tests pin the states.
- **Seed balance.** Oak Tree history must make Riverside lead Participation without changing 7.2 compliance levels; the cluster week must stay untouched by rules; month boundaries ("this month" when today is the 1st) need care: place this-month activity between the London month start and now, and at least one event on the current day when the window is empty.
- **Browser storage.** IndexedDB quotas vary (VERIFY on phones); the 50 MB cap and compression mitigate it.
- **Camera and HEIC.** iPhone photos are usually converted to JPEG by the file input, but not always; `createImageBitmap` may fail on HEIC in some browsers. Show a friendly message and suggest a screenshot (checklist item).
- **.ics import** differs between Apple, Google and Outlook calendars; the unit tests check RFC structure only (checklist item).
- **Placeholders** (grace 7 days, cap 3, offsets, small site 3, new starter 14, file limits, trial 14 days, formerly 90 days, first aider threshold 2, working-day highlight 3) need user review.
- **Accepted provider names and approver checklists** are generic and VERIFY.
- **Simulated security.** Two-factor, payments and AI are mocks; the UI must label them Demo so nobody mistakes them for real controls.
